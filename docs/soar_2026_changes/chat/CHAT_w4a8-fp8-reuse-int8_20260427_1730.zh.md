## 第 7 轮 — 现有 W4A8 INT8 kernel 能否复用为 W4A8 FP8？

### 用户提问
1. "在尝试混合 NVFP4/FP8 KV 之前回头讨论一下 w4a8(fp8 不是 int8)（成本高不高）。"
2. "我记得你提过 sgl-kernel 中有 w4a8(int8) kernel 存在，对吗？"
3. "如果是的话，能不能简单地把 kernel 函数里所有 int8 用 fp8 替换？"
4. "如果不能，为什么？要做多少事、做哪些事才能实现 w4a8(fp8) kernel ops (gemm?)？"
5. 然后："如果还没记录请记录，然后两个都做一下供我评审。"

### Agent 回答 / 操作
- 确认现有 kernel：[sgl-kernel/csrc/gemm/qserve_w4a8_per_group_gemm.cu](../../sgl-kernel/csrc/gemm/qserve_w4a8_per_group_gemm.cu) 及 per-channel 兄弟版本是稠密 W4-INT8 GEMM（QServe 风格，SM80+）。
- 解释"简单 INT8→FP8 替换"**不可行**——MMA 指令一行可改，但 W4 反量化内循环必须端到端重写，因为 QServe 刻意把反量化保留在整数算术，让结果直接喂 INT8 IMMA 而不离开整数流水。FP8 需要 `int4 → fp16 → 乘 fp16 group scale → 编码 FP8 e4m3 比特模式（符号 + 4 位指数偏置 7 + 3 位尾数，含饱和）`。
- 列出全部需要改的事项：
  1. MMA 指令 `s32.s8.s8.s32` → `f32.e4m3.e4m3.f32`
  2. 累加器 `int32_t` → `float`
  3. **反量化内循环全重写**（主要工作量）
  4. group scales 存储 int8 → fp16
  5. 架构目标从 sm_80 提升到 sm_89/90+/120
  6. SM120 tile/stage 重新调优
  7. 激活 FP8 quantizer 接线
  8. 加载器路径
  9. sgl-kernel binding + Python 包装
  10. sglang 量化 linear 方法
  11. 数值验证（FP8 e4m3 3 位尾数精度风险）
- 估计**现实 3–4 周**，官方分**+8–15%**。
- 对比备选项：NVFP4 KV 缓存 EV 更高（1 周、风险低、有冠军组合证据）。
- 用户"记录 + 两个都做"指令后，创建三对文档：
  - `ANALYSIS_w4a8_fp8_kernel_feasibility_20260427_1730.{en,zh}.md` — 可行性分析（本轮）
  - `PROPOSAL_NVFP4_KV_CACHE_20260427_1730.{en,zh}.md` — NVFP4 KV 缓存完整提案
  - `PROPOSAL_W4_FP8_CUTLASS_SPIKE_20260427_1730.{en,zh}.md` — 1 天 spike 验证 FP8 上限
- 以及本会话日志（双语）。

### 结果
- **复用现有 INT8 kernel 路径确认不可行**——需要 3–4 周（kernel 重写）。
- **两份提案待评审**：
  1. NVFP4 KV 缓存作为下一轮迭代（~1 周，推荐）。
  2. CUTLASS W4-FP8 spike（~1 天，可选；在投入 3–4 周前降风险）。
- 等待用户批准任一启动。
