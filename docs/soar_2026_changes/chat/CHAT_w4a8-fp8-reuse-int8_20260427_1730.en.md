## Round 7 — Can we reuse the existing W4A8 INT8 kernel for W4A8 FP8?

### User asks
1. "Let us back to discuss on w4a8(fp8 not int8) before try mixed kv cache NVFP4/FP8 (it is cost high or not)."
2. "I remember you mentioned there is kernel for w4a8(int8) existing in sgl-kernel, am I right?"
3. "If this is the case, can we simply modify the kernel function to replace all int8 usage to fp8?"
4. "If not, why? How many and what things need to to do to implement w4a8(fp8) kernel ops (gemm?)"
5. Then: "Pls document if u haven't and then do both in sequence for my review."

### Agent answers / actions
- Confirmed existing kernels: [sgl-kernel/csrc/gemm/qserve_w4a8_per_group_gemm.cu](../../sgl-kernel/csrc/gemm/qserve_w4a8_per_group_gemm.cu) and the per-channel sibling are dense W4-INT8 GEMMs (QServe-style, SM80+).
- Explained "simple INT8→FP8 replace" is **not feasible** — MMA opcode change is one line, but the W4 dequant inner loop must be rewritten end-to-end because QServe deliberately kept the dequant in integer arithmetic so its output feeds INT8 IMMA without leaving the integer pipeline. FP8 needs `int4 → fp16 → multiply fp16 group scale → encode FP8 e4m3 bit pattern (sign + 4-bit exp bias 7 + 3-bit mantissa, with saturation)`.
- Listed all required changes:
  1. MMA opcode `s32.s8.s8.s32` → `f32.e4m3.e4m3.f32`
  2. Accumulator `int32_t` → `float`
  3. **Dequant inner loop full rewrite** (the dominant work)
  4. group scales storage int8 → fp16
  5. Architecture target raised from sm_80 to sm_89/90+/120
  6. SM120 tile/stage retuning
  7. Activation FP8 quantizer wiring
  8. Loader path
  9. sgl-kernel binding + Python wrapper
  10. sglang quant linear method
  11. Numerical validation (FP8 e4m3 3-bit mantissa accuracy risk)
- Estimated **3–4 weeks** realistic effort, **+8–15%** official-eval gain estimate.
- Compared cost vs alternatives: NVFP4 KV cache wins on EV (1 week, lower risk, champion-combo evidence).
- After user's "document + do both" request, created three doc pairs:
  - `ANALYSIS_w4a8_fp8_kernel_feasibility_20260427_1730.{en,zh}.md` — feasibility analysis (this round)
  - `PROPOSAL_NVFP4_KV_CACHE_20260427_1730.{en,zh}.md` — NVFP4 KV cache full proposal
  - `PROPOSAL_W4_FP8_CUTLASS_SPIKE_20260427_1730.{en,zh}.md` — 1-day spike to validate FP8 ceiling
- And this chat log pair.
