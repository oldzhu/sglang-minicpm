# P1 Survey result — NVFP4 KV cache plumbing in sglang

**Date**: 2026-04-28
**Status**: Survey only. No code changes. Drives P2 plumbing plan.
**Predecessor**: [PROPOSAL_NVFP4_KV_CACHE_20260427_1730.en.md](PROPOSAL_NVFP4_KV_CACHE_20260427_1730.en.md)

## TL;DR

- **Existing plumbing reaches ~80%** of what we need: server arg, dtype config, FP4 KV pool, quant/dequant utility — all already in tree.
- **Real gaps are 100% inside our custom MiniCPM attention backend**: 4 gates that currently switch on `kv_cache_dtype_str.startswith("fp8")` need to also trigger for `fp4_e2m1`, plus interactions between `MHATokenToKVPoolFP4.set_kv_buffer`'s built-in scaling and the MiniCPM `set_kv_buffer(... layer.k_scale, layer.v_scale)` call.
- **Important labeling correction**: sglang's `fp4_e2m1` is **MXFP4** (per-16-element block, e8m0/uint8 shared exponent), not NVFP4 (e2m1 + e4m3 fp32 per-tensor scale). For our use this is a feature, not a bug — MXFP4's hardware-friendly layout is what SM120 supports anyway.
- **Estimated P2 effort**: 2–3 days of source edits + smoke test, then accuracy validation. Concentrated in one file: `python/sglang/srt/layers/attention/minicpm_backend.py`.

### 1.1 Server-arg surface
[python/sglang/srt/server_args.py](../../python/sglang/srt/server_args.py) lines 2720–2724:

"--kv-cache-dtype",

### 1.2 Runtime dtype resolution
[python/sglang/srt/model_executor/model_runner.py](../../python/sglang/srt/model_executor/model_runner.py) lines 1553–1561 (`configure_kv_cache_dtype`):

Resolves to `torch.float4_e2m1fn_x2` if PyTorch ≥ 2.8 supports it. **Need to verify PyTorch version on fcloud.**

### 1.3 FP4 KV pool allocation
[python/sglang/srt/model_executor/model_runner_kv_cache_mixin.py](../../python/sglang/srt/model_executor/model_runner_kv_cache_mixin.py) lines 56, 90, 486, 582:
```python
if is_float4_e2m1fn_x2(self.kv_cache_dtype):
    self.token_to_kv_pool = MHATokenToKVPoolFP4(...)  # or MLA variant
```
Triggered automatically by the dtype check. ✅

### 1.4 The FP4 KV pool itself
[python/sglang/srt/mem_cache/memory_pool.py](../../python/sglang/srt/mem_cache/memory_pool.py) lines 1085–1210, class `MHATokenToKVPoolFP4`:
- Allocates K/V buffers as **uint8** with shape `(m, n, k//2)` → **2 packed FP4 values per byte** = K-dim halved.
- Allocates separate scale buffer of shape `(m, (n*k)//16)` uint8 → **1 byte per 16 K-dim elements** (MXFP4 e8m0 shared exponent).
- `set_kv_buffer`: pre-scales by k_scale/v_scale if provided, then calls `KVFP4QuantizeUtil.batched_quantize` to compress to FP4 + scale factors.
- `_get_key_buffer/_get_value_buffer`: calls `KVFP4QuantizeUtil.batched_dequantize` to return **BF16** dense tensors.

### 1.5 MXFP4 quant/dequant utility
[python/sglang/srt/layers/quantization/kvfp4_tensor.py](../../python/sglang/srt/layers/quantization/kvfp4_tensor.py) — `KVFP4QuantizeUtil`:
- `batched_quantize`: `[B, M, N]` BF16 → `([B, M, N/2] uint8 packed FP4, [B, M*N/16] uint8 e8m0 scale)`.
- `batched_dequantize`: inverse.
- Both are `@torch.compile` PyTorch (no custom CUDA kernel). **Performance unknown** — needs measurement at first plumb.

### 1.6 Memory math (per token, per layer, MiniCPM-SALA shape)
For `head_num=8` (KV heads after TP), `head_dim=128`:

| Storage | Bytes/token/layer | vs BF16 | vs FP8 |
|---|---|---|---|
| BF16 | 8 × 128 × 2 × 2 = 4096 | 1.0× | 2.0× |
| FP8 e5m2 | 8 × 128 × 2 × 1 = 2048 | 0.5× | 1.0× |
| MXFP4 (FP4 + e8m0 scale) | 8 × 128 × 2 × 0.5 + 8 × 128 × 2 / 16 = 1024 + 128 = **1152** | **0.28×** | **0.56×** |

→ **~44% reduction vs FP8** (close to the 50% projection in the proposal).

## 2. The real gaps (P2 work concentrates here)

### 2.1 Gap A — sparse-scorer bf16 bridge gate (MUST FIX)
[python/sglang/srt/layers/attention/minicpm_backend.py](../../python/sglang/srt/layers/attention/minicpm_backend.py) line 834:
```python
if self.kv_cache_dtype_str.startswith("fp8"):
    if query_layer.dtype != torch.bfloat16:
        query_layer = query_layer.to(torch.bfloat16)
    if compressed_k is not None and compressed_k.dtype != torch.bfloat16:
        compressed_k = compressed_k.to(torch.bfloat16)
    ...
```
Sparse top-k scorer requires fp16/bf16. With `fp4_e2m1` the gate is False, so quantized inputs would feed the sparse kernel and crash or produce garbage.

**Fix**: change gate to `kv_cache_dtype_str in ("fp8_e5m2", "fp8_e4m3", "fp4_e2m1")`. Or better, key off `self.kv_cache_dtype_str != "auto" and self.kv_cache_dtype != torch.bfloat16` — i.e., "anything compressed needs the bridge".

### 2.2 Gap B — `use_fp8_sparse_scratch` flag (REVIEW)
Line 189:
```python
self.use_fp8_sparse_scratch = self.kv_cache_dtype_str.startswith("fp8")
```
Used elsewhere (need to grep call sites in P2) to decide whether sparse intermediate buffers are FP8 or original. With fp4_e2m1, this is False → falls back to original dtype scratch (BF16). That's likely safe (no FP4-aware scratch path exists), but adds memory. **Action**: leave False for P2; revisit only if scratch memory becomes a constraint.

### 2.3 Gap C — k_descale handling (REVIEW)
Lines 952–960 and 1173–1180:
```python
if self.kv_cache_dtype_str != "auto" and layer.head_dim <= 256 and self.fa_impl_ver != 4:
    if layer.k_scale is not None:
        descale_shape = (forward_batch.batch_size, layer.tp_k_head_num)
        k_descale = layer.k_scale.expand(descale_shape)
        v_descale = layer.v_scale.expand(descale_shape)
```
For FP8, `layer.k_scale` is the scalar quantization scale that the FlashAttention kernel uses to dequant K/V on-the-fly. For FP4, two issues:
1. Our pool's `_get_key_buffer/_get_value_buffer` already returns **BF16** dequanted tensors. So passing k_descale to FA on top of BF16 would double-scale.
2. The MXFP4 layout has **per-16-element block scales**, not a per-tensor scalar. There is no single k_scale that meaningfully describes it.

**Fix**: when `kv_cache_dtype == fp4_e2m1`, force `k_descale = v_descale = None` (skip the FP8-style scale path entirely). The FA kernel will receive already-dequanted BF16 K/V from `get_kv_buffer`.

### 2.4 Gap D — `set_kv_buffer` k_scale interaction (REVIEW)
`MHATokenToKVPoolFP4.set_kv_buffer` does:
```python
if cache_k.dtype != self.dtype:
    if k_scale is not None:
        cache_k.div_(k_scale)
    ...
    cache_k, cache_k_fp4_sf = KVFP4QuantizeUtil.batched_quantize(cache_k)
```
MiniCPM passes `layer.k_scale, layer.v_scale` (typically the FP8 quantization scale loaded from the model). If these are populated for FP8 quant config but the KV is now FP4, the pre-divide would scale K incorrectly before MXFP4 quant.

**Fix options**:
- (a) When `kv_cache_dtype == fp4_e2m1`, our backend passes `None, None` instead of `layer.k_scale, layer.v_scale` to `set_kv_buffer`.
- (b) Or set `layer.k_scale = layer.v_scale = None` at quantization-init time when KV is FP4.

Option (a) is more localized. Lines to edit: 932, 1144 in `minicpm_backend.py`.

### 2.5 Gap E — get_kv_buffer return path (VERIFY ONLY)
MiniCPM calls (lines 1055, 1180):
```python
key_cache, value_cache = forward_batch.token_to_kv_pool.get_kv_buffer(layer)
```
`get_kv_buffer` is the parent class method. Need to verify `MHATokenToKVPoolFP4` inherits it correctly and that it routes through `_get_key_buffer/_get_value_buffer`. **Action in P2**: read `MHATokenToKVPool.get_kv_buffer` to confirm; if not, override in FP4 pool.

### 2.6 Gap F — CUDA-graph capture compatibility (VERIFY)
`KVFP4QuantizeUtil.batched_quantize/dequantize` uses `@torch.compile`. CUDA-graph capture of `torch.compile`-d functions is sometimes fragile. **Action**: test cudagraph capture in P2 smoke; if it breaks, switch the utility to a Triton kernel (still 1-2 days extra).

### 2.7 Gap G — sparse_kernel forward (VERIFY)
The 3rdparty sparse_kernel (compressed_attention, infllmv2) is invoked in `get_topk_for_sparse`. After Gap A fix it sees BF16 inputs, but we should sanity-check no other code path inside it assumes FP8.

## 4. Open questions for user before P2

1. **PyTorch version on fcloud** — does it have `torch.float4_e2m1fn_x2`? (PyTorch 2.8.0+). If not, P2 needs a fallback or a torch upgrade first.
2. **Approve P2 starting from "smoke test with `--force-dense-minicpm`"?** This bypasses all sparse-attention gates, gives a clean isolated MXFP4-KV signal first; sparse re-enable comes later.
3. **Tolerance for accuracy regression**: original proposal said "target normalized > 99% (C=1.0); 97–99% acceptable if speed gain wins". MXFP4 KV is more aggressive than NVFP4 (1× e8m0 byte vs 1× fp32+e4m3 per scale block). What's the exact accept/reject threshold?
