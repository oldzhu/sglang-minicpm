# P1 调研结果 —— sglang 中 NVFP4 KV cache 的 plumbing 现状

**日期**：2026-04-28
**状态**：仅调研，无代码改动。驱动 P2 plumbing 计划。
**前序**：[PROPOSAL_NVFP4_KV_CACHE_20260427_1730.zh.md](PROPOSAL_NVFP4_KV_CACHE_20260427_1730.zh.md)

## TL;DR

- **现有 plumbing 完成度约 80%**：server arg、dtype 配置、FP4 KV pool、量化/反量化工具都已在代码里。
- **真正的缺口 100% 集中在我们的 MiniCPM 自定义注意力后端**：4 个目前以 `kv_cache_dtype_str.startswith("fp8")` 作为门控的判断需要扩展到 `fp4_e2m1`；以及 `MHATokenToKVPoolFP4.set_kv_buffer` 内置缩放与 MiniCPM 调用 `set_kv_buffer(... layer.k_scale, layer.v_scale)` 的交互。
- **重要标签纠正**：sglang 的 `fp4_e2m1` 实际是 **MXFP4**（每 16 元素一组、e8m0/uint8 共享指数），不是 NVFP4（e2m1 + e4m3 fp32 per-tensor scale）。对我们而言这是优势——MXFP4 的硬件友好布局正是 SM120 支持的。
- **预估 P2 工作量**：2–3 天源码改动 + 冒烟测试，再做精度验证。绝大多数集中在一个文件：`python/sglang/srt/layers/attention/minicpm_backend.py`。

### 1.2 运行时 dtype 解析
[python/sglang/srt/model_executor/model_runner.py](../../python/sglang/srt/model_executor/model_runner.py) 第 1553–1561 行 (`configure_kv_cache_dtype`)：
```python
elif self.server_args.kv_cache_dtype == "fp4_e2m1":
    if hasattr(torch, "float4_e2m1fn_x2"):
        self.kv_cache_dtype = torch.float4_e2m1fn_x2

```
若 PyTorch ≥ 2.8 支持，则解析为 `torch.float4_e2m1fn_x2`。**需要确认 fcloud 的 PyTorch 版本**。

### 1.3 FP4 KV pool 分配
[python/sglang/srt/model_executor/model_runner_kv_cache_mixin.py](../../python/sglang/srt/model_executor/model_runner_kv_cache_mixin.py) 第 56, 90, 486, 582 行：
```python
if is_float4_e2m1fn_x2(self.kv_cache_dtype):
    self.token_to_kv_pool = MHATokenToKVPoolFP4(...)  # 或 MLA 变体
```
由 dtype 检查自动触发。✅

### 1.4 FP4 KV pool 本身
[python/sglang/srt/mem_cache/memory_pool.py](../../python/sglang/srt/mem_cache/memory_pool.py) 第 1085–1210 行，类 `MHATokenToKVPoolFP4`：
- K/V buffer 分配为 **uint8**，形状 `(m, n, k//2)` → **每字节 2 个打包 FP4** = K 维减半。
- 单独 scale buffer，形状 `(m, (n*k)//16)` uint8 → **每 16 个 K-dim 元素 1 字节**（MXFP4 e8m0 共享指数）。
- `set_kv_buffer`：若提供 k_scale/v_scale 则先按其除一遍，再调用 `KVFP4QuantizeUtil.batched_quantize` 压缩为 FP4 + scale。
- `_get_key_buffer/_get_value_buffer`：调用 `KVFP4QuantizeUtil.batched_dequantize` 返回 **BF16** 稠密张量。

### 1.5 MXFP4 量化/反量化工具
[python/sglang/srt/layers/quantization/kvfp4_tensor.py](../../python/sglang/srt/layers/quantization/kvfp4_tensor.py) —— `KVFP4QuantizeUtil`：
- `batched_quantize`：`[B, M, N]` BF16 → `([B, M, N/2] uint8 打包 FP4, [B, M*N/16] uint8 e8m0 scale)`。
- `batched_dequantize`：反过来。
- 都是 `@torch.compile` 的 PyTorch（无自定义 CUDA kernel）。**性能未知**——首次 plumb 时需测量。

### 1.6 内存计算（每 token、每层，MiniCPM-SALA 形状）
取 `head_num=8`（TP 后 KV head 数）、`head_dim=128`：

| 存储 | 字节/token/层 | vs BF16 | vs FP8 |
|---|---|---|---|
| BF16 | 8 × 128 × 2 × 2 = 4096 | 1.0× | 2.0× |
| FP8 e5m2 | 8 × 128 × 2 × 1 = 2048 | 0.5× | 1.0× |
| MXFP4（FP4 + e8m0 scale） | 8 × 128 × 2 × 0.5 + 8 × 128 × 2 / 16 = 1024 + 128 = **1152** | **0.28×** | **0.56×** |

→ **比 FP8 减少 ~44%**（接近提案中的 50% 预测）。

## 2. 真实缺口（P2 工作集中处）

### 2.1 缺口 A — sparse-scorer bf16 桥接门控（必须修）
[python/sglang/srt/layers/attention/minicpm_backend.py](../../python/sglang/srt/layers/attention/minicpm_backend.py) 第 834 行：
```python
if self.kv_cache_dtype_str.startswith("fp8"):
    if query_layer.dtype != torch.bfloat16:
        query_layer = query_layer.to(torch.bfloat16)
    if compressed_k is not None and compressed_k.dtype != torch.bfloat16:
        compressed_k = compressed_k.to(torch.bfloat16)
    ...
```
sparse top-k scorer 要求 fp16/bf16。`fp4_e2m1` 时门控为 False，量化输入会喂给 sparse kernel，导致崩溃或乱码。

**修复**：把门控改为 `kv_cache_dtype_str in ("fp8_e5m2", "fp8_e4m3", "fp4_e2m1")`；或更优：`self.kv_cache_dtype_str != "auto" and self.kv_cache_dtype != torch.bfloat16` —— 即"任何压缩格式都需桥接"。

### 2.2 缺口 B — `use_fp8_sparse_scratch` 标志（待复审）
第 189 行：
```python
self.use_fp8_sparse_scratch = self.kv_cache_dtype_str.startswith("fp8")
```
P2 需 grep 调用点，确认 sparse 中间 buffer 走 FP8 还是原 dtype。`fp4_e2m1` 时为 False → 退回原 dtype（BF16）scratch。多用一点内存但应安全（无 FP4-aware scratch 路径）。**动作**：P2 保留 False；除非 scratch 内存成为约束再处理。

### 2.3 缺口 C — k_descale 处理（待复审）
第 952–960 与 1173–1180 行：
```python
if self.kv_cache_dtype_str != "auto" and layer.head_dim <= 256 and self.fa_impl_ver != 4:
    if layer.k_scale is not None:
        descale_shape = (forward_batch.batch_size, layer.tp_k_head_num)
        k_descale = layer.k_scale.expand(descale_shape)
        v_descale = layer.v_scale.expand(descale_shape)
```
FP8 时 `layer.k_scale` 是标量量化 scale，由 FlashAttention 在线反量化 K/V 用。FP4 时两个问题：
1. 我们的 pool `_get_key_buffer/_get_value_buffer` 已经返回 **BF16** 反量化张量。再传 k_descale 给 FA 会双重缩放。
2. MXFP4 是**每 16 元素 block scale**，不是 per-tensor 标量，没有有意义的单一 k_scale。

**修复**：当 `kv_cache_dtype == fp4_e2m1` 时，强制 `k_descale = v_descale = None`（完全跳过 FP8 风格的 scale 路径）。FA kernel 直接接收 `get_kv_buffer` 返回的 BF16 K/V。

### 2.4 缺口 D — `set_kv_buffer` 的 k_scale 交互（待复审）
`MHATokenToKVPoolFP4.set_kv_buffer` 中：
```python
if cache_k.dtype != self.dtype:
    if k_scale is not None:
        cache_k.div_(k_scale)
    ...
    cache_k, cache_k_fp4_sf = KVFP4QuantizeUtil.batched_quantize(cache_k)
```
MiniCPM 传 `layer.k_scale, layer.v_scale`（FP8 量化 scale 来自模型）。若这些值在 FP8 量化配置下被填充但 KV 已是 FP4，预除会在 MXFP4 量化前把 K 不正确地缩放。

**修复方案**：
- (a) `kv_cache_dtype == fp4_e2m1` 时后端传 `None, None` 而非 `layer.k_scale, layer.v_scale` 给 `set_kv_buffer`。
- (b) 或在量化初始化时若 KV 为 FP4 则把 `layer.k_scale = layer.v_scale = None`。

(a) 更局部。要改的行：`minicpm_backend.py` 932, 1144。

### 2.5 缺口 E — get_kv_buffer 返回路径（仅验证）
MiniCPM 调用（1055, 1180 行）：
```python
key_cache, value_cache = forward_batch.token_to_kv_pool.get_kv_buffer(layer)
```
`get_kv_buffer` 是父类方法。需确认 `MHATokenToKVPoolFP4` 正确继承，且会路由到 `_get_key_buffer/_get_value_buffer`。**P2 动作**：读 `MHATokenToKVPool.get_kv_buffer` 确认；若否则在 FP4 pool 中重写。

### 2.6 缺口 F — CUDA-graph capture 兼容性（待验证）
`KVFP4QuantizeUtil.batched_quantize/dequantize` 用 `@torch.compile`。`torch.compile` 函数的 cudagraph capture 有时较脆弱。**动作**：P2 冒烟测试 cudagraph capture；若失败则把工具改为 Triton kernel（额外 1–2 天）。

### 2.7 缺口 G — sparse_kernel forward（待验证）
3rdparty sparse_kernel（compressed_attention、infllmv2）在 `get_topk_for_sparse` 中调用。修复缺口 A 后它接收 BF16 输入，但仍应再 sanity-check 内部不假设 FP8。
